# Design Docs

This section contains the technical design documentation for our platform. Each document describes the architecture, rationale, and trade-offs behind key system decisions.

## What's in Here

Design docs serve as a living record of how the system was designed and why. They capture context that code alone cannot — the alternatives considered, the constraints that drove decisions, and the expected behavior under edge cases.

## Document Lifecycle

All design docs go through the following stages before being considered authoritative:

1. **Draft** — Author is actively writing; content may be incomplete or change significantly.
2. **In Review** — Shared with stakeholders for feedback; open for comments.
3. **Approved** — Reviewed and accepted; serves as the source of truth.
4. **Superseded** — Replaced by a newer document; kept for historical reference.

## Contributing

To propose a new design doc, open a pull request with a new `.mdx` file under `docs/`. Use an existing approved doc as a template and make sure to include the motivation, considered alternatives, and any open questions.
